1. Propósito de este documento

Este manual reúne todo lo necesario para que la web de Doria Clinic (doria.clinic) pueda seguir editándose, manteniéndose y creciendo de forma autónoma, sin depender de una sola persona.

Se escribió pensando en un escenario concreto: que el dueño actual del conocimiento técnico (Nacho) deje de estar disponible por el motivo que sea, y que el responsable de Doria Clinic necesite saber, sin ayuda externa, tres cosas: qué se puede tocar, cómo se toca, y a quién pedir ayuda para lo demás.

1.1 A quién va dirigido

Tiene dos lectores distintos en mente:

  • El propietario de la clínica, sin conocimientos técnicos: las secciones 2 a 5 y 13 a 15 son las que le interesan. Explican cómo editar textos, precios, fotos y datos de contacto desde un panel visual, sin tocar código.
  • Un desarrollador contratado en el futuro para hacer cambios de diseño o funcionalidad: las secciones 6 a 12 documentan la arquitectura técnica completa para que pueda ponerse al día en minutos, no en días.
Idea clave

La web no depende de ningún programa instalado en ningún ordenador concreto. Todo vive en internet: el contenido en GitHub, el sitio publicado en Netlify, el DNS en Cloudflare, el dominio registrado en Dinahosting. Cualquier persona con las cuentas correctas puede seguir editando la web desde cualquier navegador, en cualquier ordenador.

2. Resumen ejecutivo: cómo funciona todo, en una página

La web de Doria Clinic es una web estática: no tiene una base de datos tradicional ni un servidor que haya que mantener. Cada página se genera de antemano a partir de archivos de texto y se sirve ya "montada", lo que la hace muy rápida y prácticamente inmune a caídas por sobrecarga.

El circuito completo, de principio a fin, es este:

  1. Alguien edita un texto, precio o foto desde el panel visual en doria.clinic/admin (el CMS, ver sección 5), o un desarrollador edita directamente el código.
  2. Ese cambio se guarda automáticamente como una "versión" (commit) en un repositorio de GitHub — el archivador central de todo el contenido y el código, con historial completo de cada cambio hecho jamás.
  3. Netlify detecta el cambio en GitHub y reconstruye la web entera automáticamente (típicamente en 1-3 minutos).
  4. La nueva versión se publica sola en doria.clinic, sin que nadie tenga que "subir archivos" a ningún sitio ni reiniciar ningún servidor.
Cambio de proveedor de alojamiento (17 de septiembre de 2026)

La web se alojó inicialmente en Cloudflare Pages. Se migró a Netlify porque algunos operadores españoles (Movistar, Vodafone, Orange...) bloquean, por los bloqueos judiciales contra el fútbol pirata, rangos de IP compartidos de Cloudflare que dejaban la web inaccesible de forma intermitente para parte de las visitas — un problema ajeno al contenido de la web (detalle completo en la sección 13). Cloudflare se mantiene únicamente como gestor del DNS del dominio (ver sección 8).

Las 5 piezas del engranaje

  • Dinahosting — solo el registro legal del dominio doria.clinic.
  • Cloudflare — únicamente el DNS del dominio (ya no aloja la web).
  • Netlify — aloja y publica la web.
  • GitHub — guarda el código y todo el contenido, con historial.
  • Sveltia CMS — el panel visual de edición, en /admin.

Coste mensual de infraestructura

  • Netlify: plan gratuito (0 €).
  • Cloudflare (solo DNS): plan gratuito (0 €).
  • GitHub: repositorio privado, plan gratuito (0 €).
  • Dinahosting: solo la renovación anual del dominio.
  • Sveltia CMS: software libre, sin coste.
El proyecto de Cloudflare Pages (doria-clinic-web.pages.dev) se dejó creado pero sin usar como posible respaldo — se puede eliminar sin ningún impacto en la web real.

4. Seguridad: dónde están (y dónde no están) las contraseñas

Este manual no incluye ninguna contraseña real, de forma deliberada. No es un descuido ni una omisión: un documento PDF puede acabar reenviado por email, guardado en un ordenador compartido, impreso o subido sin querer a algún sitio — y en ese momento, cualquier contraseña escrita en él deja de ser secreta. Guardar contraseñas en texto plano dentro de un documento es, en la práctica, casi lo mismo que no tener contraseña.

Qué hacer en su lugar

  • Usar un gestor de contraseñas (1Password, Bitwarden o similar) para guardar el usuario y la contraseña de cada servicio de la tabla de la sección 3.
  • Compartir el acceso a ese gestor con al menos una persona de confianza adicional (un "contacto de emergencia"), para que la continuidad no dependa de una sola persona.
  • Activar la verificación en dos pasos (2FA) en Google, GitHub y Cloudflare, y guardar los códigos de recuperación de cada una también en el gestor de contraseñas.
  • Si se pierde el acceso a una cuenta y no hay contraseña guardada, casi todos estos servicios permiten recuperar el acceso a través del correo electrónico asociado (de ahí la importancia de proteger doriaclinicweb@gmail.com, señalada en la sección 3).
Nota sobre este documento

Una contraseña de Dinahosting fue compartida puntualmente por chat durante una sesión de trabajo con Claude. Por la misma razón explicada arriba, esa contraseña no se guardó en ningún sitio por parte del asistente — ni en este manual, ni en ninguna memoria persistente. Si esa contraseña sigue siendo válida y no está ya en un gestor de contraseñas, es buen momento para guardarla ahí y, si se comparte de nuevo por chat en el futuro, considerar cambiarla después.

5. Guía de edición desde el panel (CMS)

El día a día de la web — precios, textos, fotos, horarios, datos de contacto — se edita desde un panel visual llamado Sveltia CMS, sin tocar ni una línea de código.

5.1 Cómo entrar

  1. Ir a https://doria.clinic/admin
  2. Pulsar «Iniciar sesión con GitHub» (Login with GitHub)
  3. Iniciar sesión con la cuenta de GitHub doriaclinicweb (o con la cuenta personal, si esta tiene acceso de colaborador al repositorio)
  4. El panel muestra las «colecciones» de contenido a la izquierda
Importante

Cada vez que se pulsa «Guardar» (Save/Publish) en el CMS, el cambio se publica en la web real automáticamente en 1-3 minutos, sin ningún paso adicional. No existe un modo "borrador invisible" salvo que se use explícitamente el flujo de revisión del CMS.

5.2 Especialidades Editable en CMS

11 especialidades (Odontología general, Endodoncia, Implantes dentales, Traumatología dental, Estética dental, Ortodoncia, Periodoncia, Odontología deportiva, Odontopediatría, Cirugía oral, Prótesis dental), cada una con una entrada independiente por idioma (español, catalán, inglés — 33 entradas en total). Campos editables: título, subtítulo, resumen, resumen corto (para la tarjeta de la home), orden en el menú, si se muestra en la home, icono, especialista responsable, imagen de cabecera, preguntas frecuentes, y los datos de SEO (título y descripción para Google, y la opción de ocultarla de los buscadores). El cuerpo de texto largo se edita como contenido enriquecido (Markdown).

5.3 Tratamientos Editable en CMS

22 tratamientos, también con una entrada por idioma (66 entradas). Además de los campos de especialidades, incluye: precio desde, meses de financiación, duración de la sesión, número de sesiones, tipo de anestesia, especialista que lo firma, situaciones en las que se indica, proceso paso a paso, preguntas frecuentes, y casos de antes/después (solo debe subirse un caso si existe el consentimiento del paciente firmado y archivado — hay una casilla obligatoria para confirmarlo). También incluye la fecha de última revisión del contenido.

5.4 Equipo Editable en CMS

4 fichas de equipo (Dr. Guillermo Doria, Dra. Inés Doria, Dra. Mariana Ettedgui, Laura Rojas), cada una en un único archivo con campos separados para cada idioma cuando aplica. Editable: nombre, número de colegiado (dato real y verificado, nunca inventar), orden de aparición, foto, cargo (3 idiomas), titulación (3 idiomas), especialidades que trata, biografía corta (3 idiomas, la que aparece en la home y en la ficha lateral), trayectoria completa —uno o varios párrafos— (3 idiomas, el texto principal de su página propia), y agenda de congresos/cursos/ponencias con fecha y enlace opcional (3 idiomas).

5.5 Inicio (Home) Editable en CMS

Titular de portada (admite saltos de línea manuales: cada línea nueva que se escriba en el campo se respeta tal cual en la web), entradilla, fotos del carrusel de portada, texto del botón principal, frase y párrafos de introducción, títulos de las secciones de Tratamientos y Equipo, título y texto de Instalaciones, imágenes de Instalaciones, y SEO de la portada.

5.6 Páginas de listado Editable en CMS

Las páginas «Todas las especialidades» y «Todos los tratamientos» (por idioma): título, entradilla, preguntas frecuentes propias de esa página, y SEO.

5.7 Páginas sueltas (legales) Editable en CMS

Aviso legal, Política de privacidad y Política de cookies, en los 3 idiomas: título, entradilla, fecha de última actualización, SEO, y el contenido completo como texto enriquecido (Markdown).

5.8 Ajustes generales de la clínica Editable en CMS

Es el único archivo de datos que no es «contenido de una página», sino configuración que se usa en todo el sitio a la vez (aparece en el CMS como «Datos de la clínica»): nombre, teléfono, teléfono de urgencias, WhatsApp, email, dirección completa, coordenadas del mapa, horarios, el módulo «Tu primera visita» (título, texto, botón y puntos, en 3 idiomas — aparece en todas las páginas), el módulo «¿Por qué elegirnos?» (título y 5 razones, en 3 idiomas — también en todas las páginas), el enlace usado para pedir cita, el enlace al perfil de Google Business, el nombre exacto tal como aparece en Google Maps (para que el mapa incrustado muestre el pin con nombre), la valoración media y el número de reseñas de Google, las URL de las redes sociales, y el ID de Google Analytics (dejarlo vacío desactiva la analítica en todo el sitio).

5.9 Reseñas de Google Editable en CMS

La lista de reseñas que se muestran en el carrusel de la web (autor y texto en los 3 idiomas). Importante: estos textos son reales, copiados a mano de reseñas genuinas de Google — nunca hay que inventar ni generar reseñas de fantasía. Solo la valoración media y el número total de reseñas (sección 5.8) están pensados para actualizarse solos en el futuro (ver sección 10); el texto de cada reseña siempre se actualiza a mano.

6. Qué NO se puede editar sin programar

Todo lo que sigue requiere abrir el código del proyecto — no está disponible desde el panel visual:

  • El diseño visual: colores, tipografías, tamaños, espaciados y disposición de cualquier página.
  • El orden y la aparición de los módulos compartidos (dónde sale «Tu primera visita», el carrusel de reseñas o «Por qué elegirnos» en cada tipo de página).
  • Añadir una red social nueva a los iconos del pie de página (hay que añadir el icono en el código; una vez añadido, su URL sí se podrá editar desde el CMS).
  • Crear un tipo de página nuevo, o cambiar los enlaces del menú de navegación.
  • El comportamiento del carrusel de reseñas, el banner de cookies, el mapa incrustado, o cualquier otra pieza interactiva.
  • Las reglas de redirección del dominio o la configuración de DNS.
  • Añadir nuevos campos a una colección de contenido (por ejemplo, si mañana se quisiera añadir un campo «vídeo» a los tratamientos).

Para cualquiera de estos cambios hace falta un desarrollador con conocimientos de Astro y del ecosistema de Netlify/GitHub — o continuar usando una herramienta de programación asistida (como Claude Code) apuntando a este mismo repositorio.

7. Estructura técnica del proyecto (para desarrolladores)

7.1 Stack tecnológico

  • Astro 6 — generador de sitios estáticos; salida 100% HTML/CSS/JS, sin servidor Node en producción.
  • i18n — español (idioma por defecto, sin prefijo en la URL), catalán (prefijo /ca/), inglés (prefijo /en/).
  • Sveltia CMS — panel de edición de código abierto (sucesor espiritual de Decap/Netlify CMS), configurado en public/admin/config.yml.
  • Backend del CMS: GitHub directo — cada guardado en el panel es un commit real en el repositorio.
  • Autenticación del CMS — un Cloudflare Worker propio, sveltia-cms-auth, actúa de puente OAuth entre el panel y GitHub. Si el login del CMS deja de funcionar, este Worker es el primer sitio a revisar (Cloudflare → Workers & Pages → sveltia-cms-auth).

Particularidad importante para desarrolladores

La página de inicio (src/pages/index.astro → src/components/PaginaInicio.astro) no usa la plantilla compartida Base.astro que usa el resto del sitio: construye su propio documento HTML completo desde cero. Este es el error más fácil de cometer al tocar este proyecto.

7.4 Estilos y sistema de diseño

Un único archivo, src/styles/global.css, con variables CSS centralizadas:

  • Colores: --verde (#4D5E4F, verde principal de marca), --verde-claro (#B8BFB9), --crema (#FFFEF7, fondo claro), --tinta (#1A1F1A, casi negro).
  • Tipografías: «PP Fragment Sans» para títulos y menús, «Tiempos Text» para el titular de portada, tipografía de sistema para el cuerpo de texto.
Nota técnica pendiente

Las declaraciones @font-face apuntan a archivos /fonts/PPFragment-SansRegular.woff2 y /fonts/TiemposText-Regular.woff2 que no existen en el proyecto actualmente. El sitio funciona correctamente porque cada tipografía tiene alternativas de reserva, pero no se está mostrando la tipografía de marca original ("PP Fragment Sans", de la fundición Pangram Pangram — es la misma que se usó para dibujar el logo "Doria" de la cabecera). En el wordmark gigante del pie de página esto llegó a causar artefactos visuales (barras) con la fuente de reserva a tamaño extremo, así que ahí se forzó Georgia explícitamente como solución temporal. Para restaurar la tipografía real en todo el sitio hace falta comprar la licencia en pangrampangram.com y añadir el archivo a public/fonts/ — no es algo que se pueda generar ni obtener gratis.

7.5 Imágenes y activos

Carpeta public/img/: fotos del equipo, fotos de instalaciones (carpeta instalaciones/), logos de partners (Tu Medicina Financiada) e iconos. La carpeta public/admin/ contiene el propio panel del CMS.

8. Dominio, DNS y certificados

  • El dominio doria.clinic está registrado en Dinahosting (cuenta guillermo.doria@gmail.com). Ese registro solo cubre la propiedad legal del nombre de dominio y su renovación anual — no aloja ningún contenido web.
  • Los servidores de nombres (nameservers) del dominio son los de Cloudflare: liz.ns.cloudflare.com y matteo.ns.cloudflare.com. Cloudflare gestiona la resolución DNS del dominio, pero — a diferencia del planteamiento inicial — ya no aloja la web (ver el aviso de la sección 2 sobre el cambio de proveedor).
  • Los registros de correo electrónico (MX, SPF, DKIM, autodiscover, autoconfig — usados por Microsoft 365/Outlook para el correo de la clínica) siguen intactos en Cloudflare, configurados en modo «DNS only» (nube gris). No tocar estos registros, o el correo de la clínica dejaría de funcionar.
  • doria.clinic y www.doria.clinic son registros CNAME en Cloudflare que apuntan a apex-loadbalancer.netlify.com, en modo «DNS only» (nube gris, sin pasar por el proxy/CDN de Cloudflare). Este es el cambio clave que resolvió el bloqueo intermitente: el tráfico ya no pasa por las IPs compartidas de Cloudflare en ningún momento.

9. Repositorio de código y despliegue automático

  • Todo el código y el contenido vive en github.com/doriaclinicweb/doria-clinic-web (repositorio privado).
  • Cada guardado desde el CMS, o cada cambio de código subido por un desarrollador, se registra como un commit en la rama main.
  • Netlify está conectado a ese repositorio mediante inicio de sesión con GitHub (cuenta doriaclinicweb). Reconstruye y publica la web automáticamente en cada cambio de la rama main.
  • Configuración de construcción en el archivo netlify.toml del propio repositorio: comando npm run build, carpeta de salida dist. Al estar en el repo (y no solo en el panel de Netlify), un desarrollador nuevo puede ver la configuración de build sin tener que entrar en Netlify.
  • Las redirecciones (sección 8) se definen en public/_redirects, también dentro del repositorio.
  • El proyecto en Netlify se llama gregarious-maamoul-411d9d (nombre autogenerado; se puede renombrar desde Netlify → Project configuration → cualquier momento, sin afectar a doria.clinic).
  • El historial completo de publicaciones (deploys) se puede consultar en Netlify → proyecto → pestaña Deploys — y, si algo sale mal, cualquier versión anterior se puede volver a publicar con un clic desde ahí (rollback / «Publish deploy»), sin tocar código.
El proyecto de Cloudflare Pages original (doria-clinic-web, en doria-clinic-web.pages.dev) sigue existiendo y también se reconstruye con cada push, pero ya no recibe tráfico real — el DNS ya no apunta ahí. Se puede eliminar desde Cloudflare sin ningún efecto en la web.

10. Analítica, cookies y SEO

  • Google Analytics 4 (ID G-WG0JW6FWEC) está integrado, pero solo se activa si la persona visitante acepta las cookies analíticas en el banner de consentimiento — cumpliendo el RGPD. Se puede desactivar del todo vaciando el campo correspondiente en Ajustes (sección 5.8).
  • Cada página tiene sus propios metadatos SEO editables desde el CMS: título en Google, descripción, y la opción de ocultarla de los buscadores.
  • El sitio genera automáticamente un mapa del sitio en /sitemap-index.xml, enviado a Google Search Console para facilitar la indexación.
  • El contenido está enlazado internamente de forma extensa a propósito (especialidades, tratamientos, fichas de doctores y la página de financiación se citan entre sí) como estrategia de posicionamiento SEO.

11. Automatización pendiente: valoración de Google

Pendiente de activar

Existe un script (scripts/actualizar-resenas-google.mjs) pensado para actualizar automáticamente, una vez al mes, la valoración media y el número de reseñas de Google que se muestran en la web (sección 5.8) — sin tocar los textos de las reseñas, que siempre se actualizan a mano.

Para activarlo faltan estos pasos, todavía no completados:

  1. Crear una clave de la Google Places API (versión clásica/legacy) en Google Cloud Console — requiere una cuenta de facturación de Google Cloud, aunque el uso real de este script es mínimo y entra dentro del nivel gratuito.

13. Incidencias conocidas

Resuelto — bloqueo intermitente por operadores españoles (fútbol pirata)

Cuando la web estaba alojada en Cloudflare Pages, algunos operadores de internet españoles (Movistar, Vodafone, Orange, MásMóvil...) bloqueaban, por orden judicial contra el fútbol pirata, rangos completos de direcciones IP de Cloudflare. Como el plan gratuito de Cloudflare reparte muchísimos sitios web distintos sobre las mismas IPs compartidas, doria.clinic quedaba bloqueada como «daño colateral» para las personas que usaban esos operadores, de forma intermitente y sin que tuviera nada que ver con el contenido de la web. No era un fallo de configuración, sino un riesgo estructural de usar IPs compartidas de Cloudflare como proxy.

Solución aplicada el 17 de septiembre de 2026: se migró el alojamiento de Cloudflare Pages a Netlify (detalle en las secciones 8 y 9), manteniendo Cloudflare solo para el DNS, en modo «DNS only» — es decir, sin que el tráfico pase en ningún momento por el proxy de Cloudflare. Verificado tras el cambio: la conexión ya no se bloquea. Si en el futuro volviera a aparecer un problema similar (poco probable, ya que Netlify no está tan asociado a webs de streaming pirata en España), la solución de fondo sería conseguir una IP dedicada para el hosting.

15. Glosario de términos técnicos

TérminoQué significa
AstroEl programa (framework) con el que está construida la web. Genera páginas ya montadas, sin necesitar un servidor complejo.
CMS«Sistema de gestión de contenidos» — el panel visual (Sveltia) desde el que se edita texto sin tocar código.
Repositorio / GitHubEl archivador central donde vive todo el código y contenido, con historial completo de cada cambio.
CommitCada «versión guardada» de un cambio, con fecha, autor y descripción.
Deploy / despliegueEl proceso automático de publicar una nueva versión de la web tras un cambio.
DNSEl «listín telefónico» de internet: traduce el nombre doria.clinic a la dirección técnica real donde vive la web.
NameserverEl servicio que responde a las preguntas de DNS de un dominio — hoy son los de Cloudflare.
Registro A / CNAME / MX / TXTDistintos tipos de instrucciones dentro del DNS: A y CNAME dicen dónde está la web, MX dice por dónde llega el correo, TXT guarda verificaciones y configuración de seguridad del correo.
SSL / HTTPSEl «candado» de seguridad que cifra la conexión entre el visitante y la web.
NetlifyEl servicio que aloja y publica la web hoy, y la reconstruye automáticamente con cada cambio.
IP compartida / dedicadaUna IP compartida sirve miles de webs distintas a la vez (barato, pero con el riesgo de bloqueos colaterales explicado en la sección 13); una IP dedicada sirve solo la web de Doria Clinic.
Proxy / CDNUn intermediario entre el visitante y el servidor real, que puede acelerar y proteger la web — pero también hereda los bloqueos que afecten a su IP compartida, como ocurrió con Cloudflare.
i18n«Internacionalización» — el sistema que permite tener la web en español, catalán e inglés.
SEOEl conjunto de técnicas para que Google encuentre y posicione mejor la web.
SitemapUn listado de todas las páginas del sitio que se envía a Google para ayudarle a encontrarlas todas.
